# Release notes (draft)

Status: **draft only.** This file holds the content required for the first public source candidate (ledger todo.md items 130/131). The version number and the actual GitHub release are decided and triggered by the maintainer only — nothing in this repository tags, publishes or releases on its own.

## Purpose

Mistlane is published for **research and learning**. It is a C++20 / Lua multi-process game-server framework extracted and reorganized from a legacy game backend to study service separation, asynchronous networking, Lua embedding and dependency modernization. It is not a product, not a hosted service and not production software.

## Background and business stripping

The source material is a legacy game cluster. Everything business-specific was deliberately left behind:

- Original gameplay rules, content, configurations, assets and art are not included and are not reproduced.
- Business protocol payloads, database schemas and account/charging flows were stripped; only generic transport, session, placement, identity, record and persistence contracts remain.
- Names of roles and processes describe responsibilities (gateway, login, coordinator, gameServer, crossServer, data, apiServer), not the legacy deployment.
- Legacy evidence quoted in the documentation cites the original tree for analysis only; no legacy code is carried into this repository.

## What is explicitly not here

- **Coordinator placement is durable across a crash**: a `--journal` coordinator persists each `MLR1 ROUTE SET` character placement into the same SQLite journal as the migration snapshots; after a crash the registry restores it and answers `MLR1 ROUTE EMPTY` until the hosting member re-registers, so a login re-query can resume the chain instead of starting over. The graceful member-retirement path still clears a placement (routes follow live members).
- **No durable persistence beyond the SQLite stores**: the coordinator journal, the data-side record store (`MLD1`, `ACK durable` only with `--journal FILE`; without it receipts stay volatile), the acceptance store and the entity-state transport (`MLD2`) all persist through SQLite journals that survive restarts; the home final-sequence authority (`HomeSequenceAuthority`, `include/mistlane/record.hpp`) and its restart-restored `MLD1 FENCE` tombstone are implemented. No other backend exists — swapping the store is untested, and Oracle MySQL versions stay in the unvalidated list.
- **No sender-side durable replay**: the cross-return retry queue and the entity save path survive reconnects and drain in order on the store-backed `ACK durable` (settlement holds the leave-edge final account until then), but the queued-not-yet-acked changes live in the serving process — a sender crash loses them unless an application reconstructs and replays the submissions.
- **No hosting-generation internal caller in the attribution chain**: owner, client, server and cross callers are attributed; the hosting generation's own internal invocation is the one documented unattributed caller (see the research note in [entity contract](./docs/entity-contract.md)).
- **Partial entry authentication**: the decided `MLT1` ticket is wired end to end — a `login` configured with `MISTLANE_TICKET_SECRETS` issues it from Lua (`mistlane.ticket.issue`), and a `crossServer` with the same secrets verifies it on the join (`context.verified`). It still does not constitute durable character authorization: ticket claims stay per process and volatile (placement grants, by contrast, are journaled). Platform callbacks authenticate through the wired `MLA1` contract (durable acceptance only when `--journal` is set, replay claims stay per process); other identity today is trusted-network plus the optional `MLS1` shared token (plaintext comparison, not mTLS).
- **No spatial AOI, chunk streaming or seamless partitioning**: requirements only, see the [big map](./docs/big-map.md) page.

## Unvalidated boundaries

Per the validation records, the following are **not** validated: the original game cluster and business behavior, production load capacity (the container stress and profiling numbers are single-host, co-tenant, single-window deployment-environment evidence — not capacity claims), soak stability, platforms other than the tested Linux environment, full game migration, and Oracle MySQL versions. These results support research and learning; they do not establish production readiness.
