# MMO / distributed game server engine capability survey

> Survey date: 2026-10-19. The goal is comparing entity contracts, replication, persistence, process topology, map scaling and cross-server play — not simply comparing network libraries.
> **Method**: when source is visible, local source takes priority; official material supports only the features it explicitly describes. Public marketing, a material catalog, or a product's existence does not prove an architectural capability. `unverified` means no first-hand evidence supporting a conclusion was found this pass — not that the product necessarily lacks the feature.

### 2. KBEngine — completeness: partial (A–E, G have code evidence; F partial)

**A Contract**: `entity_defs/*.def` declares properties' `<Type>`, `<Flags>`, `<Persistent>`, defaults and Base/Cell/Client methods; `entities.xml` decides whether an entity has Base, Cell, Client. Entity-definition initialization code builds the flags mapping, and property descriptions record flags/persistent/type. Example formats are in this repo's existing KBEngine definition document and the local template files; the current template `Account.def` is an empty-properties example and must not be used as proof of a field set. [K1][K2]

**B Sync**: `Proxy::initClientBasePropertys()` initially sends Base client data to the client; `Witness::update()` batch-builds update bundles for view entities while the player's client exists, sending property/position snapshots when entities enter view; `Entity::` property updates reach the Witness per visibility flags and view/detail level, encoded as property UID/alias + serialized value. Own vs other clients' ranges are distinguished by flags; the Cell's `Witness`/View is the AOI filtering entry. The evidence supports "initial snapshot + subsequent per-property deltas", not arbitrary full-field sends every frame. [K3][K4]

**C Persistence**: `EntityTableMysql::initialize()` picks fields from `getPersistentPropertyDescriptions()` and builds mapping items per entity type; `EntityTables::load()` walks entity script modules to initialize EntityTables and `syncToDB()` syncs table structure; `DBTaskWriteEntity` hands serialized data to EntityTables and returns results. Property-set-driven per-entity-type table/field sync is provable; cross-entity multi-table atomic transactions, property-split-table rules and reliable scheduled auto-save cannot be asserted from this code. `ENTITYCALL` persistence is turned off. [K5][K6]

**D Topology**: the local source has separate `loginapp`, `baseappmgr`, `baseapp`, `cellappmgr`, `cellapp`, `dbmgr` server modules; BaseApp listens on the external client interface, CellApp on the internal interface; Dbmgr initializes EntityDef and global/base/cell data. Components use the engine's Network/Bundle, message interfaces and internal addresses rather than one monolithic server loop. [K7][K8]

**E Map**: `SpaceMemory` manages entities, spatial coordinate nodes and world enter/leave; CellApp has the Space/coordinate structure and Witness updates. Current evidence is insufficient to reduce "space/ghost replication across multiple CellApps" to seamless player cross-chunk migration, and insufficient for generic answers about switch latency or client loading. [K4][K9]

**F Cross-server**: the source shows entity and client control can be orchestrated by server components/EntityCall/migration APIs, but this pass did not fully trace the public repo's cross-server battlefield/matchmaking/player-migration business chain or persisted-data ownership. So it cannot be claimed as a built-in cross-server solution; overall **partial/unverified**. [K7][K10]

**G Players and NPCs**: the same EntityDef mechanism defines game entities, and Proxy is the type with client-connection semantics; Base and Cell each hold entity-side state, associated via client/witness. `giveClientTo()` can rebind client control to another Proxy (the source only proves that API path; automatic reconnect on disconnect and cross-process migration completeness must not be inferred from it). [K1][K3][K10]

## Cross-cutting observations

### Observable consensus

1. **The authoritative side of real-time simulation and the responsibility for data persistence must be distinguished**: KBEngine decouples Base/Cell from DBMgr; UE's Dedicated Server authoritative semantics do not come with a business DB; Nakama explicitly separates match state logic from the Storage API. The lesson is defining state owners, save triggers and ACKs — not copying component names. [K7][K6][U1][N1][N2]
2. **Network sync needs interest/receiver filtering**: KBEngine's Witness/View + flags, UE's relevancy/Replication Graph and Nakama's relevant-peer broadcast solve subscription at different granularities. Full broadcast is usually not the default for large scenes; concrete AOI structures are not a universal standard. [K3][K4][U2][U3][N1]
3. **"Map chunking" has several meanings**: asset/Actor streaming, gameplay Scene/Match rooming, and server-side simulation-authority sharding are different problems. UE World Partition evidences the first, Nakama Match evidences room-based play; neither can be called BigWorld-style seamless server-side spatial migration without additional implementation. [U5][N1]
4. **Declarative entity models help generate sync/serialization metadata but bring schema constraints**: KBEngine's `.def` describes types, sync flags and persistent fields together; UE's reflection/replication description leans toward the network object model; Nakama Match customizes state in code. The more automated, the more version-migration and compatibility management is needed.

### Major schools and their trade-offs

| School | Representative | Benefit | Cost/boundary |
|---|---|---|---|
| **Engine-grade entity runtime + multi-role processes** | KBEngine; BigWorld cannot serve as a factual comparison this pass due to missing material | Entity schema, replication, space and saving can form unified conventions; scale by responsibility processes | Inter-component RPC/migration/failure recovery is complex; schema binds deeply to the framework; BigWorld's specific trade-offs unverified |
| **Transactional/object-oriented server middleware** | Darkstar/Reddwarf | Object lifecycle and transaction/persistence APIs have middleware-level abstraction | Not a ready-made MMO AOI, seamless map or cross-server entity engine; the historical source's maintenance state and today's production suitability need separate evaluation |
| **Authoritative match / game backend platform** | Nakama | Fits rooms, matchmaking, real-time play, accounts and metadata backends; clear business-logic entry points | Game state structures and entity sync are mostly defined by business code; persistent-world sharding is a different layer |
| **Engine built-in networking** | Unreal Dedicated Server | Game objects, replication and content tooling integrated; fits instance servers/project-defined backends | The Dedicated Server itself does not solve operations-grade MMO data ownership, cross-server, online migration or character DB; World Partition cannot replace server shards |
| **Vendor-built (sparse public material)** | Tencent public course sample | Concrete project engineering experience can be learned from public talks | Outside parties cannot audit complete code and boundaries; when public material is insufficient, record "unverified" — never derive architecture from a product/company name |

## Implications for Mistlane

Mistlane's current docs assign `gameServer / crossServer / data / coordinator` as service responsibilities, not as an implemented MMO runtime; the current code is mainly generic network forwarding, Lua execution, routing and admission, and the full Avatar/Scene/save chain is still unimplemented. [M1][M2]

### Adopt directly (as design constraints, not immediate implementation)

1. **Define authority and data ownership before implementing migration**: each Avatar has exactly one writable owner at a time; define read/write boundaries between home data and temporary cross-region simulation servers, migration snapshots, generation/ACK and failure compensation. This aligns with Mistlane's existing single-writer/ownership goals. [M1][M2]
2. **Split property declaration into independent orthogonal policies**: at least distinguish network sync audience/AOI, persistence, client writability, and update frequency/precision. "Client-visible" must not auto-derive to "savable" or "client-modifiable". KBEngine's flags+Persistent is a reference model, but its flags enum need not be copied verbatim. [K1][K3][K5]
3. **Use different paths for delta sync and enter-view snapshots**: on entering AOI give a stable entity initialization snapshot, then encode by change; give broadcasts explicit receiver sets, throttling and byte caps. Validate at small scale after Mistlane's entity/scene contract matures; do not start with arbitrary world sharding. [K3][K4][M2]
4. **Auditable persistence schema/write-back**: persistent-field whitelist, serialization version, dirty tracking, async batched writes, idempotent keys, error/timeout callbacks and durable confirmation defined separately. Entity state persistence and strongly consistent records like trades/mail must not merge into one automatic ORM. [K5][K6][N2]
5. **Land cross-server first as instance/battlefield matching**: Nakama-style ticket/match is close to Mistlane's existing crossServer room membership/over-capacity refusal model; matchmaking, capacity and entry boundaries can be validated — but a successful match is not a completed player-entity migration. [N3][M2]
6. **Keep interface boundaries toward external adapters**: consider the UE ecosystem as a possible client/instance service rather than treating Unreal Actor network replication as Mistlane's server-side property/DB contract; map asset loading also does not replace server-side simulation owner handoff. [U2][U5]

### Not to copy directly

- **Do not copy BigWorld's Base/Cell process split directly**: this survey obtained no BigWorld local source or sufficient first-hand material, and Mistlane's Base/Cell-equivalent duties are undefined/unimplemented. Discuss spatial process splitting only after load profiling and the ownership/migration protocol mature.
- **Do not treat UE World Partition as distributed simulation**: it manages Actor/Level data loading; official material does not prove multiple dedicated servers sharing continuous world state. [U5]
- **Do not equate Nakama Match lifecycles with persistent character entities**: Match is a play/state-machine API; player characters' long lifecycles, cross-match ownership and reconnect recovery should be defined separately by Mistlane's Avatar/data contracts. [N1][N2]
- **Do not copy KBEngine's implicit save assumptions**: current evidence confirms persistent descriptions and DB write tasks but cannot derive that arbitrary property changes land in the database promptly. Mistlane should define dirty, save requests, commit/confirmation, crash windows and recovery rules explicitly. [K5][K6]
- **Do not extrapolate internal architecture from vendor talk titles**: the Tencent sample only proves public course material exists; until concrete talk transcripts/recordings are obtained and checked, all seven dimensions stay unverified. [T1]
