# Mainstream MMO server engines: an eight-angle design analysis and portable highlights

> Verification date: 2026-10-19. This document compares BigWorld, KBEngine, Project Darkstar/RedDwarf, Pitaya (Go), the Unreal dedicated server, and NetEase's Pomelo. They are not the same kind of product: Unreal is a game-engine network layer, Pitaya/Pomelo are distributed server frameworks, RedDwarf is a transactional Java server platform; "the engine does not provide it" must not be inferred as "the project cannot implement it".

## Scope, evidence levels and version limits

- **BigWorld local source not obtained**: the task-designated `/home/cui/workspaces/kbengine/BigWorld-Engine-14.4.1/` is an empty directory (0 files). This document therefore does not claim to have read local 14.4.1. BigWorld implementation references use the public BigWorld 2.0.1 source mirror at a pinned commit and the archived BigWorld 2.1 (2012) guides; they prove only the mechanisms those versions/documents state, not that 14.4.1 is necessarily the same.
- **KBEngine local source**: references the current checkout at `/home/cui/workspaces/kbengine` with absolute paths and line numbers. Statically reading code is not the same as having run failure/load tests.
- **"OpenDarkstar/Mirrors" identity unverified**: the exact `github.com/OpenDarkstar/Mirrors` returns 404 and no mirror confirmable as the same project was found. To avoid fabrication, the relevant section analyzes only the verifiable Project Darkstar successor **RedDwarf Server** (its repo README explicitly says formerly Project Darkstar) and does not claim it is the Mirrors the user meant.
- **Pitaya**: evidenced by the official Go framework repository and Read the Docs documentation; it is a distributed multiplayer-game server framework, not a complete MMO engine with built-in world partitioning/entity databases.
- **Domestic vendor public solutions**: NetEase's open-source Pomelo was chosen (README notes NetEase contribution, Node.js, distributed multi-process, plugins and admin tooling). It serves as a public framework design sample and does not represent the production architecture of all NetEase-operated MMOs.
- **Unverified** means current evidence is insufficient to confirm; **insufficient material** means public material lacks detail; **the engine has no such design** only means no built-in solution was found within that product's boundary — a project may still implement it separately.

## BigWorld

### Eight angles

1. **Failure recovery**: it is confirmable that the old programming guide treats player-entity persistence and database disaster recovery as server duties and introduces the secondary database with snapshot/consolidation tooling; but that is not the same as a WAL, transaction log or per-input rollback. BigWorld 14.4.1's exact CellApp/BaseApp crash recovery order, RPO/RTO and partition arbitration are unverified. Sources: [Server Programming Guide §9][bw-db], [Server Operations Guide][bw-ops].
2. **Scaling**: BigWorld's signature approach splits one Space into multiple Cells hosted by CellApps; CellAppMgr adjusts BSP boundaries by load, entities offload across boundaries, and ghosts keep the data copies adjacent Cells need. The benefit: a single large space scales horizontally by adding CellApps; the cost: boundary synchronization, migration and ghost traffic — a hotspot that cannot be spread by moving boundaries remains a bottleneck. This conclusion cites only the old mirror/guides and is not extrapolated to 14.4.1. Sources: [BigWorld BSP-related source (2.0.1 mirror)][bw-bsp], [Cell/Space guide][bw-cell].
3. **Hot reload**: the archived programming guide has Python script-reload APIs/flows; that updates behavior code and does not mean entity property types, network fields or DB schema can migrate safely without downtime. The costs and guarantees of those are unverified. Source: [BigWorld scripting guide][bw-reload].
4. **Debug observability**: the public old source has Watcher/Nub and ForwardingWatcher paths for cross-component watcher query/set; these are development/ops diagnostic interfaces, not Prometheus long-term time series, distributed tracing or audit. The version coverage of AOI visualization and recording is unverified. Sources: [WatcherNub][bw-watcher], [ForwardingWatcher][bw-forward].
5. **Programming model**: DataDescription/entity declarations coexist with Python entity scripts; methods are declared per Base, Cell, Client execution context, reducing business scripts' need to re-implement cross-tier forwarding. The corresponding cost is understanding multi-side replicas, Mailbox/EntityCall and script lifecycles for one entity's behavior. Version boundary: [BigWorld guide][bw-guide].
6. **Network layering**: the BigWorld 2.x programming guide, while comparing secondary DB consolidation in the database chapter, explicitly states inter-server-process communication uses UDP; the same guide/source mirror shows its message definitions and binary streams are engine-own formats. The precise 14.4.1 client-facing TCP/UDP mix, reliable-transport policy and serialization compatibility rules are unverified locally. Sources: [database and communication chapter][bw-db], [2.0.1 property stream implementation][bw-property-stream].
7. **Authority and anti-cheat**: server authority is the premise of its entity execution model; the archived guide specifically warns against trusting arbitrary Python arguments from clients and allows custom physics validators. Game logic still must validate speed, cooldowns and resource changes as business rules; a generic anti-cheat detection/ban loop is unverified. Sources: [Client method/security guidance][bw-client-method], [Physics validation][bw-physics].
8. **Billing and operations**: provable items are server configuration, component runtime tools, database/secondary-database tools. Generic multi-region merges, event editors and billing settlement lack sufficient evidence; treat them as game-project/operations-platform responsibility. Source: [Server Operations Guide][bw-ops].

### Portable design highlights

| Highlight | What problem it solves | Implementation points (evidence) | When worth copying | When not applicable |
|---|---|---|---|---|
| BSP spatial partitioning + ownership offload | One process hosting the whole map hits CPU/memory ceilings | BSP leaf nodes correspond to Cells; load-driven boundary splits hand entity control over; [2.0.1 `internal_node.cpp`][bw-bsp], [Cell concept guide][bw-cell] | Huge continuous worlds with dense movement that can accept spatial boundary management | Small rooms/instances suffice; cross-Cell sync costs are high, the map is very uneven and cannot migrate |
| Adjacent ghosts as boundary read replicas | Entity interaction near Cell boundaries needs cross-process reads but not an RPC per access | Maintain ghosts only in needed adjacent regions, then Witness/AOI select client-visible state; [ghost system][bw-ghost] | Maps genuinely spanning multiple spatial workers needing low-latency boundary awareness | Pure room servers, global strongly-consistent transactions, or when replication cost exceeds interaction benefit |

## KBEngine

### Eight angles

1. **Failure recovery**: Cell-side `backupCellData()` digests persistent properties and backs changed Cell state to Base via messages: `/home/cui/workspaces/kbengine/kbe/src/server/cellapp/entity.cpp:1129-1180`. The BaseApp game tick calls the Backuper, processing entities in batches by `backupPeriod`: `.../kbe/src/server/baseapp/baseapp.cpp:560-583`, `.../baseapp/backuper.cpp:25-93`. After a CellApp dies, Base creates `RestoreEntityHandler` and restores spaces/entities step by step: `.../baseapp/baseapp.cpp:694-729`, `.../baseapp/restore_entity_handler.cpp:89-185`. These are in-memory copies/periodic backups, not a WAL; the state guarantees under BaseApp crash or simultaneous loss of both processes are unverified.
2. **Scaling**: CellAppMgr's `findFreeCellapp()` skips processes opted out of balancing and picks among active candidates by lower load, then fewer entities: `.../kbe/src/server/cellappmgr/cellappmgr.cpp:230-263`; new Space creation goes through this election/load-balancing path: `.../cellappmgr/cellappmgr.cpp:328-392`. This proves new Spaces can be spread by adding CellApps; it does not prove a running Space auto-splits into multiple Cells — that behavior is unverified. A single-Space hotspot may be limited by one CellApp.
3. **Hot reload**: `KBEngine.reloadScript(fullReload)` reaches `EntityApp::reloadScript()`, reloading EntityDef, running `onReloadScript` and the entry script's `onInit(1)`: `.../baseapp/baseapp.cpp:5090-5127`, `.../lib/server/entity_app.h:1451-1469`. Ordinary vs full reload differ in definition/property-contract impact; code hot-loading does not auto-fix stale cached Python objects and does not auto-migrate the online DB schema. Runtime risk lives at script reference holders; safe-migration guarantees are unverified.
4. **Debug observability**: the built-in Watcher reads process variables by path, with Profile/Logger/WebConsole; SpaceViewer has the WebConsole connect to CellApps and periodically pull Space/Cell entity views: `.../kbe/tools/server/webconsole/WebConsole/views_spaceviewer.py:21-90,122-136`; the underlying viewer pushes via timers and streams: `.../kbe/src/server/cellapp/space_viewer.cpp:35-92,161-220`. The Watcher Python client sends path requests and parses typed values: `.../kbe/tools/server/pycommon/Watcher.py:15-40,70-140`. Generic timeline replay/trace is unverified.
5. **Programming model**: the server embeds CPython in a C++ process/entity runtime; business entity scripts participate via Base/Cell execution contexts and callbacks. `entity_macro.h`'s assignment entry type-checks then calls `onDefDataChanged`: `.../kbe/src/lib/entitydef/entity_macro.h:810-825`; the Cell-side persistent dirty marking/property broadcast is at `.../cellapp/entity.cpp:658-710`. The benefit is fast script iteration and a centralized contract; the cost is C++/Python object lifecycles, the GIL/old Python dependencies and reload reference management.
6. **Network layering**: `Channel` defaults to TCP but provides a KCP subtype; KCP initialization uses a UDP peer and KCP parameters: `.../kbe/src/lib/network/channel.h:76-82,225-250`, `.../network/channel.cpp:233-260,338-370`. A WebSocket handshake switches to the WebSocket packet reader/filter: `.../network/channel.cpp:1060-1093`. Logical messages are framed by `Bundle::newMessage()` per the message table, then written into the own `MemoryStream`/DataType — not a protobuf-default schema: `.../lib/network/bundle.h:70-103`, `.../lib/entitydef/property.cpp:82-108` (DataType serialization chain).
7. **Authority and anti-cheat**: client method execution must match the contract and check parameters, and the method receiver also verifies the entity is alive, real, has a Witness/client, and the target entity is in view: `.../kbe/src/server/cellapp/client_entity_method.cpp:53-113`. These are runtime boundary checks, not an anti-cheat system; speed, damage, drops and payment semantics still must be validated server-side. Client input is a request, not trusted state.
8. **Billing and operations**: WebConsole, Watcher, centralized logs, component management and DB write tools are the engine's operations base; a `charge` Python interface registration is visible at `.../kbe/src/server/baseapp/baseapp.cpp:440-453`, but business settlement, idempotent ledgers and payment callback verification are not automatically guaranteed by that interface. Multi-region merge/event config is not verified as generic engine capability.

## OpenDarkstar / Mirrors (verifiable substitute evidence: RedDwarf Server)

### Eight angles

1. **Failure recovery**: material on the exact OpenDarkstar/Mirrors is insufficient. The verifiable RedDwarf is an archived successor of Project Darkstar; its `TransactionScheduler` runs tasks inside transactions; `TransactionImpl` provides participant prepare/commit/abort, and `WatchdogServerImpl` tracks failed nodes and marks recovery. Whether a WAL/disk snapshot exists depends on the concrete DataStore configuration; do not equate the transaction interface with a WAL. Sources: [RedDwarf README][rd-readme], [TransactionScheduler][rd-scheduler], [TransactionImpl][rd-txn], [Watchdog][rd-watchdog].
2. **Scaling**: `NodeMappingService` maps identities to available nodes; identity/service state allows coordinated cross-node resource ownership; ClientSessionService has a session relocation flow. What scales is identity/session capacity, not AOI-spatial automatic Cell splitting. Sources: [NodeMappingService][rd-nodemap], [ClientSessionService][rd-session].
3. **Hot reload**: no safe hot-swap mechanism for service logic/ManagedObject contracts was found; material on deploying new applications/nodes while migrating existing objects online is insufficient, so no hot-update claim is made.
4. **Debug observability**: the Profile Listener can output periodic snapshots (thread counts, successful/total tasks etc.) to a server socket; code comments state the functionality is limited, not a full profiler. JMX/service statistics are also available. Source: [SnapshotProfileListener][rd-profile].
5. **Programming model**: Java `KernelRunnable` tasks execute in transactions under the scheduler, and `DataService`/ManagedObject manage persistent object references. Application logic is not a generic Python/Lua entity-callback model. Sources: [Task scheduler][rd-scheduler], [DataService][rd-data].
6. **Network layering**: the public SimpleSgs protocol encodes application messages with opcodes, string/byte arrays and `ByteBuffer/MessageBuffer`; ClientSession rides Java NIO channels; this repo's protocol is not protobuf by default. Source: [SimpleSgsProtocolImpl][rd-protocol].
7. **Authority and anti-cheat**: the platform has Identity/Authenticator and session login/reconnect tokens; it does not provide MMO movement/economy anti-cheat rules. Client submissions should still be treated as untrusted requests and validated by the application inside transactional tasks.
8. **Billing and operations**: the service platform has node, service and session management with node migration/reconnect; multi-region merges, event configuration and commercial billing have no evidence — material insufficient.

### Portable design highlights

| Highlight | What problem it solves | Implementation points (evidence) | When worth copying | When not applicable |
|---|---|---|---|---|
| Transactional tasks as the entry point for business state writes | Avoids half-writes, race conditions and scattered retry logic when concurrent handlers mutate shared persistent objects | The scheduler creates a transaction per transactional task; participants uniformly prepare/commit/abort and failed tasks retry by policy: [Scheduler][rd-scheduler], [TransactionImpl][rd-txn] | Low-frequency but atomically consistent business data: character assets, markets, rewards, mail | Per-frame movement/AOI hot paths; transaction-conflict retries cause latency and throughput problems |
| Identity-to-node mapping and session relocation | Login/session hosting need not stay pinned to the original access node | `NodeMappingService` maintains identity→node; the session service has relocation keys/state: [NodeMappingService][rd-nodemap], [ClientSessionServiceImpl][rd-session] | Multi-node session services wanting to migrate user connections or route tasks to an identity's node | When strongly real-time spatial entities must split/migrate wholesale and connection redirection or state transfer cannot be handled |

## Pitaya (a modern Go solution)

### Eight angles

1. **Failure recovery**: etcd service discovery maintains the available server-instance list and NATS/gRPC provide RPC; these are not player-data WAL/character snapshots. How business state recovers after failure needs game/database-layer design. Sources: [Pitaya README][pitaya-readme], [Features][pitaya-features].
2. **Scaling**: connection-facing frontends are separated from RPC-only backends, scaling instances by server type; the default picks instances by target type, and custom routing functions are possible. What scales is service processes; it does not auto-split one oversized room's authoritative state. Sources: [Frontend and backend servers][pitaya-frontend], [Message forwarding][pitaya-forward].
3. **Hot reload**: the official public feature set does not describe replacing business handlers or migrating schemas at runtime; Go code typically switches via deployment versions, and Pitaya built-in no-downtime migration is unverified.
4. **Debug observability**: provides metrics grouped by route/status/server type etc., pluggable to StatsD/Prometheus; tracing can integrate Jaeger, but whether all RPCs are auto-instrumented depends on configuration. Sources: [Monitoring][pitaya-monitoring], [Pitaya README resources][pitaya-readme].
5. **Programming model**: Go handler routing, frontend/backend server types, RPC and service lifecycle hooks. Client SDKs exist; there are no built-in entity classes or AOI/space models. Sources: [Pitaya README][pitaya-readme], [Overview][pitaya-overview].
6. **Network layering**: TCP/WebSocket acceptors are replaceable/wrappable; JSON default serialization with Protobuf natively optional; internal RPC defaults to NATS, gRPC available. Client wire, server RPC and service discovery separate cleanly. Sources: [Acceptors][pitaya-acceptors], [Serializers][pitaya-serializers], [RPCs][pitaya-rpcs].
7. **Authority and anti-cheat**: rate limiting, session bind/user id and other generic components exist, but authentication/authorization, position/speed validation, trade idempotency and script-abuse defense are application responsibilities; client-submitted property values must not be trusted. Sources: [Rate limiting][pitaya-ratelimit], [Sessions][pitaya-sessions].
8. **Billing and operations**: the framework supports service discovery, admin metrics and routing extension; there is no built-in MMO multi-region merge, event delivery, character migration or billing settlement product — material insufficient / outside the product boundary.

### Portable design highlights

| Highlight | What problem it solves | Implementation points (evidence) | When worth copying | When not applicable |
|---|---|---|---|---|
| Frontend access and backend business decoupled by server type | Scaling connection capacity and scaling room/business CPU need not be the same process class | frontends hold listeners/sessions and forward by route; backends only handle RPC; etcd discovery, NATS/gRPC: [Pitaya Features][pitaya-frontend], [RPCs][pitaya-rpcs] | Clearly different service types with different load curves that want independent scaling | Small monolithic servers; or when critical-path RPC hops/discovery complexity exceed the benefit |

## Unreal dedicated server

### Eight angles

1. **Failure recovery**: a dedicated server is an authoritative game instance without local player rendering — not a persistent world database. Character-state WAL/snapshots/rollback and node failover must come from the game, storage and orchestration layers; the engine itself has no generic MMO transactional persistence. Source: [Dedicated Server setup][ue-dedicated].
2. **Scaling**: multiple dedicated server processes can host matches/instances; Replication Graph/Iris reduce per-connection actor replication overhead, but they are replication filtering and network-layer extensions, not an automatic world-partition/player-handoff cluster. Sources: [Replication Graph][ue-repgraph], [Networking overview][ue-network].
3. **Hot reload**: Live Coding/Hot Reload are development-stage C++ iteration tools, not a runtime code and entity-contract migration scheme for a running dedicated server. How game data hot-loads is project-dependent; online compatibility guarantees are unverified.
4. **Debug observability**: the network profiler, Unreal Insights and network simulation/Replay tools localize replication and latency issues; they do not provide cross-region server operations, merges or character-recovery consoles. Source: [Networking overview][ue-network].
5. **Programming model**: C++/Blueprint Actor/Component, Actor RPC, property replication, authority roles; GameMode/server logic are project-defined and server validation must not be delegated to client replicas.
6. **Network layering**: UE NetDriver defaults to UDP transport with own replication bunch/bitstream encoding, offering RPC/`NetSerialize` extension points; do not assume protobuf is generated by default. Reliable vs unreliable semantics come from replication/RPC channel settings. Overview: [Networking overview][ue-network]; concrete NetDriver configuration varies by project/version.
7. **Authority and anti-cheat**: server authority decides authoritative replicas; but server RPCs also need owner, call-rate and business-parameter validation. The dedicated server does not automatically provide game-rule anti-cheat. Actor replication documentation describes authoritative server-assigned network identity: [Replicate Actor Properties][ue-properties].
8. **Billing and operations**: the engine has dedicated server target/build/cook/run basics; multi-region, merges, event configuration, accounts/payments and character migration belong to the game's online services and operations backend, not the dedicated-server target. Source: [Dedicated Server setup][ue-dedicated].

### Portable design highlights

| Highlight | What problem it solves | Implementation points (evidence) | When worth copying | When not applicable |
|---|---|---|---|---|
| Per-connection replication relevance graphs | When actor counts grow, scanning all Actor×connection pairs per update costs too much | Replication Graph filters candidate actors per connection with reusable nodes/spatial and class groupings: [Replication Graph][ue-repgraph] | High actor counts, stable interest ranges, per-instance isolation between servers | When cross-process consistent world ownership is needed; small games where graph-node maintenance is more complex than scanning |
| Server authority + explicit RPC/property replication boundaries | Client local prediction must not directly become authoritative assets/combat state | The server writes authoritative state and replicates by owner/conditions; clients send RPCs/input requests that the server validates: [Networking overview][ue-network], [Replicate Actor Properties][ue-properties] | Games where competitive, combat and asset states need a trust boundary | It does not translate to "the engine validates your game rules for you"; business validation, rate limiting and anti-cheat must still be built |

## NetEase Pomelo (a domestic vendor's public framework)

### Eight angles

1. **Failure recovery**: the Pomelo README declares a master high-availability plugin; generic character-state persistence, transactional recovery/WAL and world-state rollback are not core guarantees. Player-state recovery after failure depends on business storage. Source: [Pomelo README][pomelo-readme].
2. **Scaling**: the distributed multi-process architecture separates connection-access servers from business backends, managing heterogeneous processes by route/server type; parallelizing an existing single room or single hot worker still needs business sharding. Sources: [README][pomelo-readme], [Pomelo Chinese overview][pomelo-cn-overview].
3. **Hot reload**: the README promises no no-downtime updates of business code/message contracts; Node.js modularity does not make runtime replacement safe, and production deployment/session-migration strategies are unverified.
4. **Debug observability**: the README lists command-line, admin, performance-test and AI tooling; actual monitoring metrics, sampling and sustained production maintenance depend on plugins/versions. Sources: [Pomelo README][pomelo-readme], [Admin/Architecture wiki][pomelo-admin].
5. **Programming model**: Node.js handler/route, request-response/broadcast, Master/Monitor and multi-process server types, built on event loops that avoid shared-state locks within one process; cross-process work still coordinates via RPC/messages. Sources: [Pomelo README][pomelo-readme], [Pomelo Chinese architecture doc][pomelo-cn-architecture].
6. **Network layering**: pomelo-protocol organizes message frames/types with TCP and WebSocket connectors; protobuf is supported by the separate `pomelo-protobuf` component and must not be read as enabled per default in every project. The dependency tree includes `pomelo-protocol` and `ws`: [package.json][pomelo-package].
7. **Authority and anti-cheat**: the framework's connection/routing and sessions do not prove business identity; client fields must be validated by handlers. Generic anti-cheat, payment security and economy validation are not claimed in the README.
8. **Billing and operations**: pomelo-admin provides a service-management base, and the README lists plugins, AI/bots and load-test tools; multi-region merges, event configuration, billing ledgers and data migration remain game/operations-system duties — no complete engine-built-in solution was found.

### Portable design highlights

| Highlight | What problem it solves | Implementation points (evidence) | When worth copying | When not applicable |
|---|---|---|---|---|
| Convention-over-configuration server types/routes | Adding a service role avoids hand-written forwarding, deployment coupling and routing boilerplate | Master/Monitor manage service types and instances; the framework forwards requests to the target server type by route; docs emphasize multi-process distribution: [Pomelo README][pomelo-readme], [Chinese architecture][pomelo-cn-architecture] | Many RPC endpoints, business services scaling by load level, teams needing fast service splits | When every call needs strong consistency or runtime schema strict validation; convention is not an authorization/idempotency guarantee |
| Admin, load-test clients and framework plugins as separate modules | Ops/load-test capability need not live inside business logic and one core package | The framework provides extensible components and admin/performance-test tools; extra capability composes by module: [Pomelo README][pomelo-readme] | Wanting to add/remove management capability per project lifecycle with one control plane | When plugins lack version governance/permission isolation; or the historical plugin stack is unmaintained or incompatible with current Node.js |

## Cross-engine common hard problems

1. **Crash consistency and experience continuity are not solvable by the network engine alone.** BigWorld/KBEngine provide recovery points through archiving/backup or DB collapse; RedDwarf puts part of the state into transactions; Pitaya/Pomelo/Unreal leave state guarantees to the application and storage. Periodic snapshots have a clear RPO, transactions pay throughput/conflict costs, and event logs need replay-version compatibility. No mechanism gets high throughput, strong consistency and fast recovery for free at once.
2. **Horizontal scaling and a single hot state are not the same problem.** BigWorld can migrate spatial boundaries but pays ghost, boundary-event and handoff complexity; KBEngine mainly places new Spaces on emptier CellApps and unproven for slicing a single space horizontally; service frameworks can add frontends/backends but do not auto-split a hot room; Unreal's Replication Graph only reduces replication work and does not change authoritative-state ownership.
3. **The hardest part of hot updates is state and contracts, not reloading code files.** KBEngine's fullReload already touches EntityDef, and Python still holds old class/callback references; other frameworks mostly leave version switching/data migration to the project; Unreal's development hot-compile tooling is not online migration. Explicit compatibility windows, version fields, rollback strategies, connection drain and old-data upgrades are required.
4. **Observability often stops at current metrics, lacking the causal chain from player input to persisted outcome.** Watcher, Pomelo admin, Pitaya metrics, Unreal Insights and RedDwarf profile each cover different layers; cross-process trace, unified entity/request correlation IDs, replay and safe online audit are not automatically closed-loop.
5. **Transport reliability is not business reliability.** TCP/KCP/RPC success only proves the corresponding layer delivered; retrying after timeout can double-charge/double-reward, and disconnection can leave server outcomes inconsistent with client beliefs. Request IDs, idempotency keys, persisted-confirmation semantics and owner generation/epoch are mandatory.
6. **Authoritative execution still needs application rule validation.** Engines can restrict who may call an RPC, which properties replicate, and what message parameter types are; whether speed/cooldown/drop/currency/payment rules are legal only business domain context can judge. Clients should provide intent, not authoritative outcomes.
7. **Commercial operations capability is often mistaken for "MMO engine capability".** Multi-region routing, merges, event configuration, payment reconciliation, offline character migration and data repair usually belong to separate operations/platform systems; public framework material generally cannot prove generic safe semantics.

## Highlights Mistlane can adopt directly (by priority)

Mistlane currently splits `gateway/login/coordinator/gameServer/crossServer/data` and explicitly has unimplemented parts in player/scene, persistence write authority and cross-region ownership (see [`architecture.md`](./architecture.md), [`process-roles.md`](./process-roles.md)). The following are design suggestions, not implemented features:

1. **P0: an authoritative collapse point and confirmation contract for persistence writes** (borrowing KBEngine's Base collapse boundary for Cell authoritative state, but not copying its in-memory-only periodic backup). Define a unique writer/generation per character; save requests need idempotency keys, database transaction boundaries, a defined meaning of success confirmation and post-timeout query/retry paths; forbid double writes when returning home data across regions. Applies to character assets/rewards/payments; not to per-tick position snapshots.
2. **P0: process transfer uses an explicit prepare → snapshot → destination-ack → route-switch → source-release state machine** (borrowing RedDwarf's identity-to-node routing and BigWorld's owner handoff). Define crash recovery, duplicate messages and a fencing epoch per step; load routing or heartbeats alone must not grant a second writer. Mistlane's transfer handshake is explicitly unimplemented — suitable to start with protocol/fault-injection tests.
3. **P1: placement by load and entity capacity, with scheduling separated from admission** (borrowing KBEngine's CellappMgr dual metrics of load/entity count). Compute effective capacity and overload rejection for online workers instead of random assignment; identify large-room hotspots separately and never assume adding processes auto-scales one room.
4. **P1: pluggable transport, serialization and explicit message contracts** (borrowing Pitaya's acceptor/serializer and Pomelo's protocol modularity). Mistlane already separates TCP/WS adapters from internal payload boundaries; keep versioning external protocol versions, internal request IDs, deadlines, error codes and schema compatibility rules — "it parses" is not compatibility.
5. **P1: development/ops live tooling layered by entity and space** (borrowing KBEngine's Watcher/SpaceViewer and BigWorld's Watcher). Start with read-only diagnostics for active session/character owner/scene distribution, replication/migration phases and persistence task state; isolate internal interfaces behind auth, bound the output, and keep full-entity dumps out of the main tick.
6. **P2: script reload replaces behavior only; state/contract migration is versioned separately** (borrowing KBEngine's reload/fullReload distinction while avoiding its stale-reference problem). Mistlane's Lua VM replacement must pair request drain/old-VM stop, new-VM init and keep-old-VM-on-failure; character data upgrades use explicit migration rather than expecting reload to rewrite player state.
7. **P2: load tests and failure drills as prerequisite evidence for scaling/recovery claims** (borrowing Pomelo/Pitaya's separate bot/test tools). Make gateway disconnects, service partitions, DB timeouts, worker crashes, duplicate payment callbacks and hotspot rooms repeatable tests, recording RPO/RTO, P99, backlog and overload rejection; a passing test is not automatically a production-capacity promise.
