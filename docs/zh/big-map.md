# 大地图：评估与需求

状态：评估与设计需求（2026-10-19），不含实现。本页回答模型页的大地图条目，把三个本质不同的问题分开，并逐条说明本仓库的证据能证明什么、不能证明什么。它先固定术语，避免后续切片把实例化、分块、AOI 与跨进程移交混为一谈，并列出流式加载与空间分区方案必须满足的需求。本页不带来任何代码改动，也不改变 CLI 行为。场景状态一侧见[场景生命周期](./scene-lifecycle.md)；旧证据见[模型页](./player-scene-model.md)与[gameServer 能力评估](./gameserver-capabilities.md)。

## 三条轴，分别评估

| 轴 | 是什么 | 证据能证明 | 证据不能证明 |
|---|---|---|---|
| 资源量 | 地图资源的体积与数量（模型、贴图、服务端障碍/导航） | 模型页已把服务端可见静态数据与客户端材质分开；场景生命周期页把服务端数据放进进程内只读缓存并按引用释放 | 分块、流式或预加载已存在，以及客户端资源到底怎么加载——客户端加载不能从服务端代码推断 |
| 活跃实体量 | 一个场景内同时模拟/观察的实体数量 | 旧代码有 AOI 式位置同步（`UPDATE_INTERVAL=1000`）与基于场景的组织方式；没有任何声称必须一个场景装下整个世界 | 任何 AOI、激活预算或模拟预算已实现、已实测或已调优 |
| 跨进程无缝 | 一个逻辑世界跨多个进程、权限转移对外不可见 | 玩家跨场景/跨进程转移是旧代码的既有路径 | 无缝空间分区、邻居状态或权限移交已存在 |

三者相互独立：小资源量也可以有大量活跃实体，大资源量也可以很少，无缝分区与两者都正交。解决其中一条绝不得被汇报成解决了另一条。

## 不可混同的机制

下面是不同的机制，证明方式各异，任何实现状态声明都不得把其中两个等同：

- **实例化** —— 从定义分配一个场景实例。能证明"场景可以创建"，证明不了分块或 AOI。
- **分块 / 流式** —— 按需交付大地图的一部分。共享静态数据的空间缓存并不等于在流式加载它。
- **AOI** —— 限制哪些实体彼此同步。它约束同步流量，不约束激活、模拟成本或整张地图的内存。
- **Avatar 跨服移交** —— 把参与者和上下文在进程间转移。搬运完整角色不等于提供无缝空间分区。
- **服务端静态数据共享** —— 一个定义服务多个实例（场景生命周期页的那个缓存）。它不等于客户端资源管理。

## 客户端与服务端加载分开

| 一侧 | 加载什么 | 在本设计中的位置 |
|---|---|---|
| 客户端 | 模型、贴图、特效；体量大、对延迟敏感 | 客户端资源管线，服务端代码之外；不能从本仓库推断 |
| 服务端 | 障碍、通行、导航、规则引用的静态数据 | [场景生命周期](./scene-lifecycle.md)页的进程内只读空间缓存 |

服务端只需要游玩决策与寻路真正会用到的静态数据。定义中仅客户端可见的材质只被引用，不会被加载进服务端缓存。因此一套流式方案要协调两个预算——服务端每次进入的字节数与客户端每个区域的字节数——两者不能互换。

## 流式加载需求（不实现）

将来若实现分块交付，必须满足：

1. **分块是交付机制，不是缓存。** 流式必须与场景生命周期页的空间缓存释放规则配合：一个流式分块要么属于该实例引用的数据，要么是缓存里可淘汰的部分，不能同时是两者。
2. **进入时不传输。** "不重复加载"规则同样适用于分块：进入或迁移不得重新下载或重新发送目标进程已经持有的数据。
3. **分块标识稳定且锁 digest。** 分块按 `(定义 ID, digest, 分块 ID)` 寻址；digest 锁定整个定义，因此分块不会在读者脚下变化。
4. **预加载与淘汰显式定义。** 方案须事先定义预加载触发条件与淘汰规则，并服从引用模型——引用了该分块的实例会保留它，淘汰不得与加载竞态。
5. **失败按请求、可重试。** 加载失败只上报给发起请求的一方；依赖它的实例准备在预算内失败或等待，绝不允许发布"带洞的就绪"状态。
6. **预算靠实测，不靠假设。** 分块大小、预加载距离与淘汰策略来自目标硬件的实测；当前环境无法可靠剖析，因此本页不给出任何数字。

## 空间分区需求（不实现）

将来若实现多进程无缝，必须满足：

1. **权限是移交，不是猜出来的。** 实体跨分区边界只在显式且被确认的移交后改变归属；漏掉的心跳或丢失的更新不得产生两个所有者，也不得留下无人负责的区间。这与[跨服回传协议](./cross-return-protocol.md)的唯一写入者纪律一致。
2. **邻居状态显式声明。** 跨分区交互若需要另一个分区的状态，必须声明出来；不得默认每个分区都能看到整个世界状态。
3. **无缝是玩家可见属性，不是代码布局。** "代码里是一张图"不等于无缝；验收标准是玩家跨越边界时观察不到归属停顿或状态重复。
4. **场景实例仍是一个写入者。** 分区解决的是实体在逻辑世界中的归属，不得为一个实例制造两个写入者——场景生命周期页的"一实例一写入者"始终成立。
5. **预算边界是激活与模拟，不是面积。** 计算量取决于分区内激活的内容，因此分区预算用活跃实体数与模拟成本表述，不用平方米表述。

## 与场景生命周期的衔接

流式与分区插入场景生命周期页的准备状态机：`preparing` 正是分块加载与分区引用解析发生的地方，`ready` 是唯一可以接受进入的状态，而任何在预算内无法完成的分块或移交都让准备失败——绝不产生"带洞的就绪"。这让本页需求与生命周期的状态一致，而不是另起一套模型。

- 地图定义的文件格式与分块在磁盘上的寻址方式：属于场景生命周期页标注的实现绑定决策。
