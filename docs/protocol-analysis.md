## Coordinator migration transaction (first slice)

Implemented on 2026-10-20 as the typed C++ protocol in `include/mistlane/migration.hpp`; no new CLI or wire verb is exposed. This is the minimal deterministic implementation for todo:48, not a complete coordinator runtime or real load balancer. `MigrationTransaction` models one participant; its colocated source lease, home facts and coordinator journal represent separate future service boundaries. Existing MLR1 registration/readiness/load/role routes remain the directory surface; router is never renamed to stand in for coordinator.

### Identity, scope and generation

`MigrationRequest` is PREPARE: `(home realm, character)`, immutable request `id`, complete `expected` route `(owner, generation)` and destination owner. Owner contains `scope.kind`, `scope.realm`, `scope.cross_group`, `role`, `instance`, `scene`. A realm scope requires only `realm` and `gameServer`; a cross-group scope requires only `cross_group` and `crossServer`. Instance and scene are required identifiers. The participant's home realm is independent of hosting scope, so transfer preserves home-data identity (and does not move the gateway). This records scene ownership identifiers, without creating scene runtime objects.

Home data alone issues generations: `HomeGenerationAuthority::reserve` advances a per-`(realm, character)` high-water mark, starting from a trusted current grant (fresh grants start at 1 per the login contract). Coordinator requests allocation, never invents a version; aborted reservations remain consumed. Every subsequent event carries `MigrationToken {key, id, generation}`. Wrong key is `Invalid`; unknown ID or mismatched generation is `Stale`; reusing an ID with changed expected owner/target is `Conflict`. One transaction per participant may be active. Identical PREPARE is `Duplicate` without allocating again, including terminal replay. `write_allowed(owner, generation)` requires the exact active home grant; route lookup alone grants nothing. This reuses `WriterLease` admission/timer/drain gates and aligns with the old-generation fence; it does not add owner-grant enforcement to the current MLD1 endpoint (gap 4).

### Commit, abort and recovery protocol

| Phase / typed message | Guard and effect | Retry / outcome |
|---|---|---|
| PREPARE / `prepare(request)` | Compare the complete expected owner AND route generation with both route and home owner; reserve next generation, stop source admission/timers, stage destination; `idle` or terminal → `preparing` | Same ID/body is `Duplicate`; concurrent or changed-body request is refused |
| `SourceDrained` | All admitted source handlers have finished; snapshot/final ordered changes are ready | Does not grant target or publish route; repeated acknowledgement is `Duplicate` |
| `HomeFence` | Requires source drain; home commits final sequence and source tombstone in the future durable implementation; model relinquishes source lease and records the fence | Irreversible; no timeout/abort can restore old generation |
| `DestinationReady` | Requires home fence; destination has loaded the fenced state and acknowledged new-generation activation | Model activates the target lease; route still points to the old owner |
| COMMIT / `Commit` | Requires fence + destination ACK + expected-route comparison; publish target route and committed outcome together | `committed`; duplicate old COMMIT never republishes over a newer route |
| ABORT / `Abort`, then `Cleanup` | Before home fence only: enter `aborting`, drain remaining work, discard staged target and restore source admission/timers under the old grant | `aborted`; cleanup is `Pending` while handlers drain; generation reservation is retained |
| RECOVER / `Recover` | Read trusted transaction/home checkpoints; before fence finish abort cleanup; after fence enter `recovering`, wait for real target ACK, then commit | No inferred ACK or revived old grant; repeated terminal recovery is `Duplicate` |

The required publication order is **source stops/drains → home data fences old generation and final sequence → destination loads/activates and ACKs → coordinator CAS-publishes route with committed outcome**. Temporary unavailability between fence and target activation is allowed. Abort before the fence rolls back routing to its unchanged source value; after the fence recovery must finish forward. If the destination cannot resume, remain recovering: target retirement/replacement needs explicit home takeover with a strictly newer generation, not a guessed failure or rollback. The retirement and abandonment half of that exchange is implemented below for everything before the home fence; the post-fence takeover still needs a durable home authority and is not modeled here.

The runtime persistence contract must atomically record the home reservation/final cursor/tombstone and the corresponding home transaction facts before exposing their acknowledgements, and persist coordinator intent plus route/terminal outcome before acknowledging COMMIT. `MigrationJournal` (see below) now covers the coordinator half — terminal IDs and consumed generations survive restart — while the home-data half (reservation/final cursor/tombstone and `ACK durable`) still has no durable store. Across services, replay/query authoritative home facts with the same token; do not trust a coordinator timeout or a missing row as proof of abort. Missing durable evidence requires staying unavailable until reconciliation, never authorizing a second writer.

The five cases `coordinator.migration.commit`, `.abort`, `.recover`, `.stale`, `.order` cover normal commit; halfway cleanup and reservation non-reuse; reconstruction at seven crash cuts (including pending post-fence recovery); late generations/old COMMIT; and early fence/activation/publication plus route CAS conflicts. The source code uses the existing `test_cases` runner. Full coordinator/data/Avatar wiring, process/scene lifecycle integration, real load balancing and durable home-data crash/retirement testing remain open.

### SQLite journal storage (first persistence slice, 2026-10-27)

Implemented in `include/mistlane/journal.hpp` and `src/journal.cpp`: the coordinator migration journal is now a SQLite file store (`--journal FILE`, coordinator role only), using the static `sqlite3` vcpkg port so the single-binary/on-disk deployment stays self-contained. `MigrationJournal::save/restore` stores one versioned snapshot per `(namespace, realm, character)`; the snapshot is the same `MigrationTransaction::Snapshot` used by the in-memory model (route/home owner, `WriterLease`, journal and current request), so a coordinator restart reconstructs the exact unresolved transaction and seeds the home authority from the highest consumed generation. `Registry` saves before replying to `MLR1 MIG` `OWNER`/`PREPARE`/`EVENT`/`COMMIT`/`ABORT`/`RETIRE` after every accepted mutation, answers `MLR1 ERR STORAGE` and closes the leg if SQLite cannot commit, and restores pending transactions before opening listeners. Terminal IDs and aborted generations are never dropped. `coordinator.migration.journal` runs two real coordinator restarts against the same file: a fenced pending transaction resumes `READY`/`COMMIT` at its original generation and the next prepare allocates the strictly next generation; a terminal abort/cleanup row is restored across restart and its consumed generation is not reused. ctest 57/57 (MariaDB external integration excluded by repo convention).

### Member retirement, destination loss and takeover (second slice)

Implemented 2026-10-20 in the same model; still no CLI or wire verb. `retire_member(token, member)` acknowledges a member leaving the registry while a transaction depends on it, and it is the pre-fence half of the takeover exchange described above.

The claim is validated before anything is trusted: the key must match the transaction and the generation must match the journal entry (otherwise `Stale`), the transaction must be current and non-terminal (otherwise `Conflict`), and `member` must be a valid owner this transaction actually depends on — either the expected source owner or the destination. A member with no part in the transaction, an unidentifiable owner claim and a cross-realm key are all `Invalid`.

| Which member retired | Effect |
|---|---|
| Source, before the home fence | The source process is gone, so its in-flight handlers can never finish. `WriterLease::drain_requests` force-completes them (refused once the lease has left `Requested`), then the transaction aborts in one step: discard the staged destination and restore the source's old grant, admission and timers. The route keeps its unchanged value |
| Destination, before the home fence | The source is still alive, so its handler still owns admission. Answer `Pending` until it finishes, then abort exactly as an ordinary abort would. The transaction never advances, and source writes stay frozen for the whole time the handoff is `Requested` |
| Either, after the home fence | `Pending`, no mutation. Ownership stays `Fenced`, the old grant stays relinquished, and `Recover` still waits for a real destination ACK |

The consumed-generation rule is what makes takeover safe rather than clever. An abort leaves its reserved generation burned, so a later PREPARE from the same route allocates the next one (9 → 10 in the test) and commits onto a *living* destination. Nothing is guessed, rolled back or revived across the fence, and `drain_requests` cannot run after the tombstone.

`coordinator.migration.retire` covers the three rows above, the lease-level force-drain assertion, the refusal matrix (unrelated member, malformed owner, stale generation, cross-realm key, terminal transaction), and a checkpoint restored across a retirement that refuses to re-issue a generation. ctest 53/53.

### Registry wire verbs (`MLR1 MIG`, third slice 2026-10-20)

Implemented 2026-10-20 on the coordinator registry leg in `src/node.cpp` (`migration_line` and the `Registry` migration map): the model above is now reachable over framed TCP, gated by MLS1 exactly like every other registry frame on a `--service-token` coordinator. Home facts arrive with `OWNER` and are adopted once per `(namespace, realm, character)` — a restatement must repeat them exactly, anything else answers `ERR CONFLICT`, and the coordinator stores facts without ever being the generation authority. The verbs are idempotent by request id: a replayed frame repeats its verdict (`PREPARED <id> <generation>`, `STEP`, `COMMITTED`, terminal `ABORTED`) without reserving a newer generation.

| Verb | Line | Verdict |
|---|---|---|
| `OWNER` | `MLR1 MIG OWNER [NS <ns>] <realm> <character> <gen> <owner>` | `OWNER OK`, `ERR CONFLICT` on disagreement, `ERR INVALID` on a shape the model would refuse |
| `PREPARE` | `... PREPARE [NS <ns>] <realm> <character> <id> <gen> <expected> <destination>` | `PREPARED <id> <next-gen>`; `ERR EMPTY` (no facts), `STALE` (never-published expected route), `CONFLICT` (changed body or concurrent request), `ORDER` (source still executing) |
| `EVENT` | `... EVENT [NS <ns>] <realm> <character> <id> <gen> <DRAINED\|FENCE\|READY\|CLEANUP>` | `STEP <id> <STATE>`; `PENDING <id>` while post-fence work waits; `ERR ORDER` for a skipped step |
| `COMMIT` | `... COMMIT [NS <ns>] <realm> <character> <id> <gen>` | `COMMITTED <id> <published-owner> <generation>` (replays included) |
| `ABORT` | `... ABORT [NS <ns>] <realm> <character> <id> <gen>` | `ABORTING <id>` (rollback scheduled), `ABORTED <id>` once terminal |
| `RETIRE` | `... RETIRE [NS <ns>] <realm> <character> <id> <gen> <owner>` | `ABORTED <id>` / `PENDING <id>` — the same claims as `retire_member` |
| `STATUS` | `... STATUS [NS <ns>] <realm> <character>` | `STATE idle <owner> <gen>`, `STATE <id> <STATE> <drained\|open> <fenced\|unfenced> <ready\|notready> <gen>`, or `MLR1 EMPTY` |

The `NS <ns>` group is optional on every verb and sits right after the verb — omitted, or `-`, names the default group; a bare positional namespace is refused here, so a frame written for the two-scope grammar keeps meaning the default group. `<owner>` is `<realm\|cross> NS <ns> <scope> <role> <instance> <scene>`, the same group as the registry verbs, so a namespaced owner never reads alike with a default-group one; identifiers reuse the registry's `[A-Za-z0-9_-]` cap (64). Lines are capped at 1024 bytes (versus 256 for the small registry frames), shape refusals reuse the registry vocabulary (`ERR INVALID`/`ERR UNEXPECTED`), and a member leaving the registry retires the live transaction that claimed its `(namespace, scope, role, instance)` — the coordinator observes it from membership, no message is needed.

**Namespace scoping (2026-10-27).** Every registry verb gained the namespace: `REGISTER` and `QUERY` take an optional group (a bare `<namespace>` positionally or `NS <namespace>`, `-` for the default), `PLACE` takes `<role> [<ns>|NS <ns>] <scope>`, `ROUTE SET`/`GET` take a **required** `NS <ns>` group — the older two-argument `ROUTE GET` is refused as `ERR INVALID` rather than reading as the empty namespace — and `MIG` takes the optional group after the verb, as above. On `QUERY` and `PLACE` an absent group means the default group too, never a cross-group listing, so two coordinators in different groups share no query surface. Route records and migration facts key on `(namespace, realm, character)`; registry membership, routes and retirement claims key on `(namespace, scope, role, instance)`, so a member leaving retires only the transaction that claimed that namespaced identity. Members select the group with `--namespace NAME` (valid only on gameServer/crossServer/login, refused without `--coordinator`, alongside `--scope`), and `mistlane.place(role, namespace?, scope?, callback)` asks for a named group — a lookup in an empty group answers `EMPTY`, never a parse refusal.

The wire inherits the model's boundaries, unchanged: a migration line carries no peer authentication beyond MLS1, the journal and generations are volatile, the coordinator never sends events on its own (DRAINED is the source's assertion, and EVENT does not distinguish which party sent it), and there is no post-fence takeover. `coordinator.migration.wire` (ctest 56/56) covers the full OWNER→COMMIT happy path, replay/stale/conflict/order refusals, CLEANUP-finished abort with burned generation, registry-driven retirement of a SIGTERM'd member, both RETIRE refusals, the MLS1 gate on a tokened coordinator with its own facts, and the shape/payload refusal matrix.

## External API surface (first slice)

Implemented on 2026-10-20 as the typed C++ protocol in `include/mistlane/api.hpp` + `src/api.cpp`, with the HTTP transport wired the same day (below). Like the migration slice above, this fixes wire semantics and the minimal deterministic implementation (`ApiVerifier`, `ApiReplayGuard`, `ApiAcceptanceStore`, `ApiSurface`) for the apiServer contract; the HTTP surface is a native `POST /mla1` intercept beside the Lua routes, still without a durable acceptance backend or a connected home-facts source. Credentials (`ApiCredential`, 32-byte secret) are injected by the embedding application from environment/local private config — no real secret exists in the repo, and nothing in chat or code is a credential.

### Request fields and signature

An `ApiRequest` signs exactly ten fields; the canonical byte string starts with the `MLA1` magic and appends each field as `u32 BE byte-length + exact bytes`, in this order — length framing means no field value can alias into a neighbor:

| # | Field | Form | Rule |
|---|---|---|---|
| 1 | `operation` | `ACCEPT` \| `OWNER` | Selects acceptance vs read-only lookup |
| 2 | `audience` | identifier | Must equal the verifier's audience |
| 3 | `principal` | identifier | Credential lookup key |
| 4 | `key_id` | identifier | Credential lookup key (rotation label) |
| 5 | `timestamp` | u64 seconds | Absolute request time, see window |
| 6 | `nonce` | exactly 32 lowercase hex digits | Caller CSPRNG; anti-replay claim key |
| 7–8 | `(realm, character)` | identifiers | Home key; `realm` must be in the credential's realm set |
| 9 | `idempotency_key` | identifier (`ACCEPT` only) | Acceptance dedup scope, see below |
| 10 | `payload` | opaque ≤ 1 MiB (`ACCEPT` only) | Forwarded inside the receipt |

The signature is `HMAC-SHA256(canonical_bytes, secret)`, compared with constant time. HMAC-SHA256 matches the repo's OpenSSL stack, and MLA1 and the login ticket both sign through the single shared `hmac_sha256` primitive over exact bytes; per-`(principal, key_id)` rows label rotation, and rotation is now decided: a row's optional `valid_until` keeps the old key verifying through that second inclusive while the new one already works, so there is no coordinated cutover; an expired row answers `UnknownCredential` exactly like an absent one, and revocation is removing the row — no tombstone, and a stale caller learns nothing beyond "not a live key". Choice of window+nonce over a caller sequence fence: platform callbacks come from independent operators that do not share sequence state, so an absolute ±300 s window plus a per-`(audience, principal, nonce)` claim set is the policy that needs no cross-caller coordination. Claims are consulted only after the HMAC passes (forgeries never evict honest claims), kept through `timestamp + window` inclusively, and the guard refuses to run on wall-clock rollback (`Clock`, fail closed). The guard is process-local memory; a multi-process deployment needs a shared/durable claim.

### Idempotent acceptance and ownership lookup

| Operation | Semantics |
|---|---|
| `ACCEPT` | Atomic create-or-read on key `(audience, principal, (realm, character), idempotency_key)`: same key+body → `Existing` with the original receipt; same key, changed body → `Conflict`; new key → `Inserted`. The receipt **is** the immutable accepted-command row (b46be86-style single-mutation insert, no check-then-insert and no business callback to repeat); one mutation makes receipt and command visible together, so exactly-once acceptance is observable as `Inserted`/`Existing`. `durability` is `Volatile` until a durable backend commits; `Durable` may only be reported after a durable commit, including on `Existing` after a lost reply |
| `OWNER` | Read-only, deterministic home-facts lookup `(realm, character) → {owner?, generation, Active\|Draining\|Fenced}` via `MigrationTransaction::lookup_ownership` — never the coordinator route, never a generation reservation or lease change. A fenced gap has no owner until the destination ACK; source keeps ownership while draining |

Verification order is validate → audience → credential → realm authorization → HMAC → replay claim; a failed check answers `Invalid`/`UnknownCredential`/`Forbidden`/`BadSignature`/`Window`/`Replay`/`Clock`/`Full` deterministically without consuming anything. `ApiSurface::handle` then dispatches `ACCEPT` to the acceptance store and `OWNER` to the lookup, returning auth + acceptance + ownership in one typed reply.

Caller: generate CSPRNG nonce → set absolute timestamp → canonicalize → HMAC → deliver. Verifier: the order above, then the operation table. A replayed request is deterministically refused (`Replay`) for as long as its original claim is unexpired; past the window it is refused as `Window` regardless.

### HTTP transport (first slice, 2026-10-20)

`POST /mla1` on any node HTTP listener is intercepted natively, before the Lua `http` callback; every other path (and `GET /mla1`) stays plain Lua routing. The request body is the canonical bytes followed by the raw 32-byte signature; parsing is byte-exact — the `MLA1` magic, exactly the ten framed fields, a decimal timestamp (`from_chars`, no overflow), then exactly 32 signature bytes with nothing after — and any deviation, including shape-valid fields that fail request validation, answers `400` with an `INVALID` verdict body rather than tripping the script. The reply body frames five words with the same `u32 BE` length scheme: auth verdict (`OK`/`INVALID`/`UNKNOWN_CREDENTIAL`/`FORBIDDEN`/`BAD_SIGNATURE`/`WINDOW`/`REPLAY`/`CLOCK`/`FULL`), acceptance word (`INSERTED`/`EXISTING`/`CONFLICT`/`FULL`/`INVALID` or empty), durability (`VOLATILE`/`DURABLE` or empty), the receipt payload verbatim (or empty), and the ownership word (`FOUND`/`NOT_FOUND` or empty). HTTP status follows the verdict: 200 for verified success outcomes, 400 `Invalid`, 401 `UnknownCredential`/`BadSignature`/`Window`/`Replay`, 403 `Forbidden`, 404 an `OWNER` lookup answered `NOT_FOUND`, 409 `Conflict`, 503 `Full`/`Clock` (clock rollback fails closed server-side; a retry may succeed once time is sane).

Enablement is env-only and all-or-nothing: `MISTLANE_MLA1_AUDIENCE` plus `MISTLANE_MLA1_CREDENTIAL`, the latter holding `;`-separated rows `principal:key_id:<64 lowercase hex secret>:realm[,realm...][:until]`, where `until` is a decimal epoch-seconds rotation bound (absent or 0 = unbounded). Half-configured or malformed credentials — a non-decimal `until` included — refuse node startup; unset variables leave `/mla1` as an ordinary Lua route. The ownership lookup is wired to nothing until home facts have a source, so `OWNER` deterministically answers `NOT_FOUND` — it never invents an owner. A native intercept adds no Lua-callback latency observation; metrics for the API surface are deferred with the durable acceptance backend.

The cases `api.rotation` covers rotation and revocation on the verifier: the old key verifies through its bound inclusive while the new one already works, an expired key answers `UnknownCredential`, a failed expiry check leaves the shared nonce slot free for the live key, and removing a row stops that key at once. `api.wire` and `api.http` cover: byte-exact round-trip of both operations, the full malformed-body refusal list (empty, magic-only, wrong magic, nine/eleven fields, lying length, leftover bytes, short signature, unknown operation, non-numeric/empty/overflowing timestamps, non-hex nonce), exact reply bytes per verdict, the status mapping table, and end-to-end on a booted apiServer — signed `ACCEPT` insert then idempotent `EXISTING` retry, `CONFLICT` on a changed body under one key, tampered-signature 401, `OWNER` 404, garbage 400, Lua fallthrough for every other route and unconfigured nodes, startup refusal for half-configured/malformed credentials and a non-decimal `until`, plus a rotation bound end to end: a row whose `until` has passed answers 401 `UNKNOWN_CREDENTIAL` while one still live answers 200 `INSERTED`.

Not done, with unlock conditions: a durable acceptance backend and multi-process replay claims (unlock: durable store transaction plus crash/lost-reply/restart tests), a connected home-facts ownership source with owner-relocation retry tests (unlock: home-data read path), Rotation and revocation are decided and tested (below).

### Entry ticket model (MLT1, first slice 2026-10-20)

The decided login ticket exists as the typed C++ model in `include/mistlane/entry_ticket.hpp`: `EntryTicket` over `(realm, character, target instance, hosting generation, expiry, nonce)` with an `MLT1`-magic canonical framing (the same `u32 BE` length scheme as MLA1, numbers as decimal text), signed with the shared `hmac_sha256` primitive under a per-realm secret — the ticket's realm keys the secret map, so two realms never share a verifier answer. `TicketVerifier::verify` answers deterministically in a fixed order — `Malformed` shape, `UnknownRealm` (secret lookup, before any signature work), `BadSignature` (constant-time compare), `Expired` strictly after expiry and valid through it inclusively, `WrongCharacter`/`WrongInstance`/`WrongGeneration` against the arriving identity, then the replay claim — and a failed check never consumes the nonce. `TicketClaims` is the bounded seen-claim table: fail-closed on wall-clock rollback, eviction only of claims past their expiry. The wire form is bound in a second slice (below): `entry_ticket_hex`/`parse_entry_ticket` render the canonical bytes plus the raw signature as hex, and the `MLC1` join carries it in the optional last participant group `tk <hex>` (`include/mistlane/cross.hpp`), which refuses the whole join rather than stripping the ticket when the hex does not decode or names a different character or hosting generation than the tail declares. A host now runs the verifier — the fourth slice below wires it onto the crossServer join path with an environment-injected secret map. What stays open: the claim table is per process and volatile — a restarted or multi-process deployment needs shared durable claims before `Replay` is honest.

The `login.ticket` case covers: issue/verify roundtrip, byte-exact canonical framing against hand-built bytes, every field moving the signature, issuer refusals on bad shape (empty instance, zero generation, short or uppercase nonce) and verifier construction refusals (no secrets, non-identifier instance), the full verdict ladder (flipped signature bit, honest-retry-after-failure, replay, wrong character/instance/generation, cross-realm secret, unknown realm), inclusive expiry, deterministic double expiry, clock rollback, and claim-table capacity.

### Entry ticket transport (`MLC1` `tk`, second slice 2026-10-20)

The ticket's wire form is the canonical `MLT1` bytes followed by the raw signature, hex encoded; the join carries it as the optional last group of the participant context tail (`include/mistlane/cross.hpp`, `entry_ticket_hex`/`parse_entry_ticket` in `include/mistlane/entry_ticket.hpp`). The join is all-or-none on the tail: a ticket that does not decode, that exceeds 1024 hex characters, that names a different character or hosting generation than the tail declares, or that an anonymous join presents at all, answers INVALID for the whole join — the context never drops the ticket from a participant that claimed one. The handshake payload cap moved from 256 to 1200 bytes so a ticket-shaped join fits; the cap still bounds what one handshake can cost.

What the transport binding does not claim: verification — that is the fourth slice, where a host configured with secrets verifies on the join path (below). Even after it, claims stay per process and no storage chain exists, so a verified join marks eligibility the script can read, not a durable write that happened, and the ownership runtime stays in gap 4. `core.contracts` covers the roundtrip, the forged-tail refusal list (odd length, non-hex, lying field length, truncated and extended blobs, over-cap tails), the identity/generation binding, anonymous joins with a ticket, a wrong tail keyword and the payload cap.

### Host-side verification (`MLT1` verify, fourth slice 2026-10-21)

Implemented 2026-10-21 on the crossServer join path in `src/node.cpp`: a host started with `MISTLANE_TICKET_SECRETS` (comma-separated `realm:<64 lowercase hex>` rows, injected through the environment like the MLA1 credentials — no loader, CLI flag or real secret ships inside the framework) verifies the join's ticket before admitting it. The verdict binds the ticket to the participant's home realm secret (the `ret` realm keys the map), the host's own `--service-name`, and the declared hosting generation; the claims table lives on the node, so a replay across connections on one process is caught. Every failed verdict refuses the whole join with one word, `MLC1 ERR TICKET` — the context never drops a claimed ticket, and a cross gateway relays the word through unchanged — while the specific reason (`replay`, `expired`, `bad-signature`, ...) goes to the operator's log only. An anonymous join stays admitted and stays read-only; a ticket on an unconfigured host also admits with no eligibility, because carrying a token is never authorization by itself. The script reads the verdict as `context.verified`, true only for a ticket verified under this host.

What this does not claim: the claims are still per process and volatile, so a ticket replayed after a restart or onto a second host of the same realm is not caught; `verified` marks eligibility for the script, not a durable write that happened (no storage chain exists); and nothing checks the ticket against the coordinator's route or generation facts — the binding is between the join's own words and the ticket. Broken configuration refuses startup, named: a bad hex row, an empty value, a non-identifier realm, a duplicated realm, a missing `--service-name`, or the variable on any non-crossServer role. `cross.ticket` covers the unconfigured host, the honest admit with `verified=true`, the replay, wrong-instance/expiry/secret refusals, the tail-binding INVALID, and the startup refusals.

## Naming and semantics aligned (with boundaries)

- The invocation key uses `scope/type_id/entity_id/incarnation`; `EntityRef` uses that same address tuple. `hosting_generation` is an ownership fence, not entity incarnation (`entity-contract.md:243–254`).
- `realm` / “origin realm” / “home region or group” refer to the data ownership domain; `scope` is coordinator placement scope. They must not be treated as interchangeable (`cross-return-protocol.md:11`, `architecture.md:70`).
- `RECEIVED` means endpoint accepted into volatile process memory; `ACK durable` means home data committed durable storage. They are explicitly different (`cross-return-protocol.md:58`, `service-contracts.md:36–41`).
- Transport correlation (`MLC2`) and entity `correlation_id` are intentionally independent; protocol errors remain surface-specific rather than sharing EntityError codes (`entity-contract.md:237–275`).
