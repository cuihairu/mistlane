# BigWorld-like protocol system: evolution notes

Status: research note, checked against repository documents on 2026-10-19. This extends the inventory and gaps in [Protocol analysis](./protocol-analysis.md); it does not repeat that audit. “BigWorld-like” means a coordinated set of contracts, codecs, transport, routing, entity replication and generated client bindings. It does not mean wire compatibility with BigWorld or KBEngine.

The external references below are research material, not existing Mistlane conclusions. Links were checked on 2026-10-19. BigWorld material is historical documentation; KBEngine is used as an open implementation/reference, not as a claim that every engine has identical behavior.

## Legacy game-fogs to Mistlane

The legacy client path is evidenced in [player and scene model](./player-scene-model.md#protocol-and-method-contracts-before-abstraction): `game/Data/Data.lua` loads binary `game/proto/sproto.spb`; `game/lib/sp.lua` encodes/decodes; `game/proto/Protocol.lua` maps names to IDs; `PacketHandler` registrations expose client handlers. The original `.sproto` text source and reproducible generation path were not located. This section maps that legacy starting point to Mistlane, rather than treating its generated binary as a source contract.

| BigWorld-like part / legacy evidence | Mistlane evidence and current position | Classification |
|---|---|---|

## sproto implementation route

Decision: use sproto for entity/RPC message encoding. XML `.def` and type files remain the handwritten contract; sproto is generated output. This follows [entity-contract.md](./entity-contract.md#design-choice), where the Server bundle includes sproto schema, Lua bindings and digests as planned artifact contents. The current build emits validated deterministic schema alongside XSD, release lock and digest, and includes a test-only Lua codec prototype; entity runtime and SDK generation are absent.

| Stage | Concrete work | Acceptance evidence shape |
|---|---|---|
| 1. XML contract to sproto schema | Keep `.def` as source; run the existing semantic checker before emission. Preserve provenance and mark original game-fogs sproto text unrecovered. Map types, fields, methods and request/response or one-way notifications; use stable `E{entityId}_{Server|Client}_{methodId}` names. cloudwu/sproto parser tags are limited to 0–32766; the current deterministic mapping is `entityId * 512 + side * 256 + methodId`, with entity ID ≤63 and method ID ≤254. | `contract.tool` verifies mappings, stable naming and repeatable output; the CLI validates first and emits XSD, lock, digest and schema only after every input passes. The upstream parser accepts generated `avatar.sproto`. |
| 2. Codec boundary and golden vectors | Keep outer transport framing separate. Use upstream cloudwu/sproto wire encoding for scalar, array, nested and boundary values. Keep the earlier fixture-only canonical TLV vectors explicitly labeled internal format. | `mistlane_sproto_wire_golden` asserts exact upstream sproto bytes for populated and empty Avatar values; `mistlane_sproto_upstream_parser` parses generated schema. `sproto.golden` remains the separate internal TLV check. |
| 3. Lua prototype and dispatch | Use the upstream Lua binding and generated schema; C++ contract descriptors dispatch by entity/side/method and pass caller and target context. Validate fields against the contract; requests return typed responses and notifications have none. | `contract.tool` covers deterministic C++ bindings, dispatch and five negative paths; `mistlane_sproto_lua_roundtrip` covers Lua codec roundtrip. |
| 4. RPC harness and lifecycle | Define correlation, timeout/cancel, duplicate handling, response ownership and stale entity-generation behavior. | In-process and two-process harness covers request/response, push, timeout, stale reference, wrong caller, disconnect and duplicate handling. |
| 5. SDK compatibility | Generate JS/C# bindings from the shared schema and compare supported client versions. | JS/C# encode/decode standard golden vectors; compatibility checks detect removed, renumbered or retyped published IDs. |
| 6. Release lock and publication gate | Persist protocol tag assignments and schema digest in the release lock; compare compatibility with a previously published bundle. | Reproducible bundle and compatibility report block breaking changes before publication. |

These are research gates, not dates or a product commitment. Phase boundaries are intentionally evidence-based: no later stage should be described as complete based solely on generated files existing.

## Implemented status and evidence

Stage 1 is implemented. Stage 2 is complete for the current fixture: `mistlane contract build` validates the XML and emits deterministic `.sproto`; the vendored upstream parser accepts it; the upstream Lua binding encodes standard wire bytes checked against fixed golden hex and decodes them back. The separate `sproto.golden` vectors remain project-internal TLV and are not represented as sproto bytes. `examples/contracts/avatar.def` is newly constructed, not recovered game-fogs source.

Stage 3 now has a Lua upstream-sproto request decode feeding the C++ `EntityDispatcher`, plus a fixture-driven entity route table with explicit duplicate-delivery, missing-entity and stale-incarnation outcomes. Generated bindings include field-specific C++ argument structs; schema and bindings are rebuilt twice and compared byte for byte. The runtime remains in-process and does not own network sockets or persisted entities.

Stage 4 has an in-process RPC lifecycle harness. It pairs by caller correlation id, expires against a supplied monotonic clock, discards late responses, rejects duplicate responses, and marks in-flight requests cancelled after disconnect. These are deterministic state-machine tests, not a production transport implementation. Envelope alignment: [entity-contract invocation fields and error vocabulary](./entity-contract.md#invocation-envelope-and-error-protocol-decided-unimplemented) (fields `scope` through payload at `docs/entity-contract.md:241–252`; closed errors at `:258–273`; validation order at `:275`). Harness behaviors retain those semantics: timeout=`TIMEOUT`, cancelled in-flight=`CANCELLED`, stale target=`STALE`, duplicate delivery/response=`CONFLICT`.

Stages 5–6 remain open: JS/C# SDK compatibility and the release-lock publication gate. Runtime loading, network dispatch, deadline propagation over a live transport, cancellation propagation, hosting-generation fencing, persistence and production capacity limits remain open beyond this harness. Evidence is in `rpc.lifecycle`, `mistlane_sproto_dispatch`, `contract.tool`, and `examples/sproto_lua.lua`.

## Scope and exclusions

This is a notebook entry in the evolution of the older `game-fogs/sproto` project. It records a possible route from the extant client sproto binary and Lua codec path toward an explicit, generated, cross-runtime protocol system. It does not claim implementation completeness, promise interoperability with BigWorld/KBEngine, or define a commercial delivery schedule. Productization, hosted service design and cloud backup are outside this note.
