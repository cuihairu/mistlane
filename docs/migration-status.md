# Migration status

This ledger distinguishes architectural ideas carried forward from code that has actually been extracted. It describes the Mistlane 0.1 candidate; it does not claim that the full legacy framework or game server has been migrated.

| Legacy capability | Mistlane status | Current boundary / next decision |
|---|---|---|
| Character hosting, Session/Avatar and transfer | Designed, not extracted | Legacy characters move between Hegel/CrossHegel while Gate keeps the connection; no Avatar type exists in the framework. The object split, lifecycle states, hook surface, migration and load/save rules are specified on the [Avatar runtime](./avatar-runtime.md) page; generic Avatar lifetime, single-writer ownership and reliable handoff remain unimplemented. See the [model](./player-scene-model.md). |
| Map definitions, spatial data and scene instances | Designed, not migrated | Legacy SceneManager/Scene are largely Lua and navigator calls are commented out; the framework has no scene, map or entity objects. The layer split, prepare states, cache reference/release and cleanup order are specified on the [scene lifecycle](./scene-lifecycle.md) page; large-map axes and streaming/spatial-partition requirements are on the [big map](./big-map.md) page. Streaming, spatial AOI and seamless execution remain requirements only. The item-by-item gameServer assessment lives in the [capability page](./gameserver-capabilities.md). |
| Cross-region changes saved at home | Partially implemented | Legacy set/setDirty routes through CrossWorld and home World to Data/Cache. The target preserves home ownership: the `data` role now answers the MLD1 home-side endpoint (`LOAD`/`SUBMIT`) with the generation fence, per-character sequence discipline and resend dedup, but it answers receipts only — no `ACK durable`. The coordinator journal half of the persistence chain is now on SQLite (`--journal`, see the [protocol analysis](./protocol-analysis.md)); the data-side durable ack and the crossServer sender with its bounded retry queue are still not implemented. See the [cross return protocol](./cross-return-protocol.md). |
| Process startup, listeners, signal handling and shutdown | Reimplemented | `Node` owns the new lifecycle; see the [lifecycle audit](#legacy-lifecycle-audit) for the item-by-item comparison. The old process API and binary compatibility are not retained. |
| Asynchronous TCP transport | Reimplemented | New four-byte length-prefixed payload protocol, per-session limits and deadlines. Old framing and client protocol are unsupported. |
| WebSocket / secure WebSocket | Replaced | Drogon/Trantor handles WS/WSS; no handwritten handshake, masking or control-frame parser is carried over. |
| HTTP server | Replaced | Drogon handles HTTP/HTTPS and Lua request handlers. The old HTTP server API is not retained. |
| HTTP client | Replaced | A bounded synchronous libcurl adapter is provided for C++ callers; it must not block an event-loop callback. |
| Embedded Lua and callbacks | Reimplemented | A module table and explicit init/start/message/http/tick/stop/shutdown hooks replace fixed legacy global callbacks; see the [Lua callback audit](#legacy-lua-callback-audit). The VM remains single-threaded. |
| Lua infinite-loop detection | Partially replaced | An instruction-count hook catches common runaway scripts. It is not a hard CPU or memory sandbox. |
| Gate / World / Hegel responsibilities | Partially extracted | Generic forwarding and Lua execution only; the current roles do not implement complete World coordination or Hegel hosting. See [process responsibilities](./process-roles.md). |
| Cross-server room routing | New minimal implementation | `gateway --routing cross`/`crossServer` provides deterministic group/room routing, epoch checks and local hard admission. It is not global admission, service discovery or player-state migration. |
| Peer connection registration, reconnect and queued delivery | Not migrated | Current sessions use direct upstream connections. The legacy handshake was traced (2026-10-18): the active side sends `sp.pack(Protocol.HandShake, {name, sidx, tarName})` from `L_FirstMsg`/`ServerService:handShakeToServer`, the accept side dispatches the first raw packet to `L_Register`, the first reply switches the connection to framed mode (`L_ServerMsg`), writes issued before the handshake are queued until then, and reconnection is a fixed 2-second timer with a `proxyOff` hook. The packet asserts identity without any authentication, so re-implementing it would add no security. Keep static `UPSTREAMS` plus the MLC1 epoch handshake; design registration/authentication together only when dynamic discovery or an untrusted interconnect is actually required. The legacy send queue was traced too: live producers are Lua `net_asyncWrite` and C++ `pushData` appending to an unbounded per-connection send list (payloads over 64 KiB split into indexed parts with only a warning), the consumer is the `async_write` chain, a disconnect destroys the list without redelivery, the pre-handshake `pushQueue` deque has no callers in the legacy tree, and reconnection retries on a fixed 2-second timer. No bounded reliable-delivery module is introduced: the legacy behavior preserved no delivery guarantee to port, so it must be specified against a concrete application requirement with explicit byte/count bounds and an overflow policy. |
| Legacy thread pool | Reuse available | Legacy concurrency was classified on 2026-10-18: the `FogsProcess` thread group is Asio I/O (`io_service::run` plus per-`IServer` loops), `HttpRequestService` runs a fixed pthread pool doing blocking `curl_easy` calls, `d_push`'s `TaskScheduler` uses a CPU-count `ThreadPool` for blocking push tasks, `d_world` embeds a Poco HTTP server thread pool (blocking), the `DeadLoopMonitor` watchdog thread was dropped in favor of the instruction hook, and legacy MySQL went through synchronous libmysqlclient calls on server threads. Mistlane keeps every hot path asynchronous (Asio I/O, Boost.MySQL/Boost.Redis pools); its synchronous curl adapter is CLI-only and documented as forbidden inside event-loop callbacks, so no blocking worker pool is instantiated today. Boost.Asio `thread_pool` remains the designated vehicle when a blocking need appears, with admission/backpressure around submissions because a worker pool alone does not define the application's queue limit or shutdown policy. |
| Lua timer queue | Reuse available | The legacy `game/Util/Timer.lua` surface was compared on 2026-10-18: `setTimeout`/`setInterval`/`remove` over a pure-Lua min-heap plus an imminent-task array (cap 100 000 tasks, sub-5-second bucket), driven by the wall-clock `L_doTick`, with `xpcall` error logging, intervals re-pushed with updated timestamps, and a magic `xx1` return that removes a failing interval. Boost.Asio `steady_timer` already supplies monotonic asynchronous timers underneath. Decision: no cancellable `timeout`/`interval` Lua API is added now — no framework-internal consumer exists, and the old design's needs (game-unit scheduling at six-figure scale) are application domain. If an application later requires it, implement a thin timeout/interval pair over `steady_timer` with registry handles, explicit cancel, a defined callback-error policy (no magic sentinels), death of pending timers on VM reload, and a bounded task count, and define per-behavior contracts first (see the pending-timer contract item). |
| Lua dead-loop monitor | Partially replaced | An instruction-count hook is present; the old monitoring thread and its stop/race behavior are not copied. |
| CPU/memory profiler | Not migrated | Neither the old framework nor Mistlane has CPU sampling, allocation profiling or Lua function-level profiling. The old Lua timeout hook is not a profiler. |
| MySQL access | Replaced at the connection-pool layer | Boost.MySQL `connection_pool` and a probe are present. No game schema, dirty-write cache, SQL helper, or general Lua async database bridge is migrated. |
| Redis client and Lua binding | Replaced/partial | Boost.Redis 1.92 is enabled from vcpkg. Optional `--redis` enables bounded asynchronous Lua Streams APIs and sorted-set leaderboard operations. `MISTLANE_REDIS_TLS=on` enables TLS with mandatory chain and dialed-name verification (`MISTLANE_REDIS_CA` pins the anchor); plaintext remains a trusted-network default. Integration coverage includes duplicate group creation, reconnect after a server restart, stale callbacks across hot reload, and TLS acceptance/rejection by CA and name. Generic command access remains future work. |
| UDP transport | Reuse available | Legacy UDP call sites were inventoried on 2026-10-18: the only server instantiation is `WorldServer::openUdpServer` exposed to Lua as `C_openUdpServer(ip, port)`, and its only Lua call site (`WorldService.lua`) is commented out; the `UdpClient` side and its `L_onUdpClientMsg`/`L_onUdpServerMsg` callbacks have no callers outside the net layer, so UDP was effectively dead in the legacy tree. Boost.Asio already provides asynchronous UDP sockets; no datagram contract or Lua adapter is added, and a use case must be confirmed before that public API exists. |
| Logging service and Lua logger APIs | Reuse available | Minimal requirements were fixed on 2026-10-18: a line carries a UTC timestamp, a level (error/warn/info, debug gated), the role, the listen address and the message; the `ready <role> <addr>` line stays a machine contract untouched; writes must be safe from the event loop, the web worker thread and async callbacks; rotation and collection default to the process supervisor (journald for stdout), with file sinks and remote aggregation left to deployment. Boost.Log 1.92 (thread-safe filters, attributes, formatters and sinks, already in the baseline) is the selected cross-role C++ facade for the day a second sink or level filtering is genuinely needed — today's ~24 direct `std::cout`/`std::cerr` call sites keep working, and Drogon and Boost.Redis keep their own loggers meanwhile. No Lua logger API is exposed until a concrete script need exists. |
| Metrics, process monitor and system information | Partial | Legacy system-info callers were inventoried on 2026-10-18: `d_common/sysinfo`'s live surface is only `initSysCounter()` as a startup boolean in six mains and `gCpuNum` sizing d_push's blocking thread pool, while the CPU-utilization sampler (`getCpuUtil`) has no live caller (`gmGetSysInfo` is commented out); `L_StateMsg` and `L_OmMsg` carry application/state and operations payloads, not system metrics. Mistlane therefore keeps the optional private `/metrics` listener as its Prometheus surface; since 2026-10-18 it exports readiness, active sessions, admission rejections, Lua callback duration, RSS, per-direction message/payload-byte counters, client-request latency, upstream error and deadline-timeout counters, and event-loop tick lag (histogram plus running max) — every metric carries the role label only, with fixed histogram bucket counts. CPU/memory observation stays with node-level collectors (cgroup, node_exporter), and no OpenTelemetry adapter or in-process sysinfo API is introduced until a concrete dashboard need exists. Internal liveness/readiness probes ship since 2026-10-18 (`--probe-listen`, the PROBE1 protocol with nonce/token auth, hysteresis-gated readiness, and cross gating on `IP:PORT[:PROBE]` upstreams); production dashboards and load validation remain. |
| Crash reporting | Partial | Optional Crashpad handler writes to a local database with uploads disabled. Install rules place `mistlane` and `crashpad_handler` side by side (2026-10-18): both need only the system runtime, and deployment documentation records the `ptrace` requirement for containers plus the colocation/database conventions. Minidump generation is proven by an automated drill (2026-10-18): the `mistlane-crash-sample` binary reproduces a controlled null dereference through the same pipeline and the native `crashpad.minidump` case asserts a real `MDMP` dump lands in the database. Retention policy remains deployment work; build-id symbol archiving ships as `tools/crash_symbols.py` with documented `minidump_stackwalk` steps (2026-10-18). |
| Crypto, compression, URL, serialization helpers | Not migrated wholesale | Game-specific helpers and custom protocol utilities are excluded. Use maintained libraries and explicit formats for concrete needs. |
| Generic Lua utility files | Selective extraction | Only MinHeap was reviewed and extracted. The remaining 23 `game/Util` candidates were screened one by one on 2026-10-18: `JSON.lua` is GPL-licensed JSON4Lua (hard exclusion under Apache-2.0); `Aes.lua`, `Rsa.lua`, `SnapShotDump.lua` and `CacheCode.lua` need external Lua libraries (luacrypto, lua-openssl, a snapshot lib, the sproto `Data` module) or commit key material in source; `Logger.lua`, `log.lua`, `SystemUtil.lua`, `Print.lua`, `MessageUtil.lua`, `StringUtil.lua`, `TableUtil.lua` and `Date.lua` depend on legacy `C_*` logging/time globals (and `Print` overrides the global `print`); `DropTableUtil.lua`, `ServerUtil.lua`, `TimeExecute.lua` and `Timer.lua`/`TimerQueue.lua` are game-domain, legacy-topology or the already-decided timer surface; `Math.lua` needs `bit32`, which the sandbox does not open; `VerificationUtil.lua` and `TimeUtil.lua` are application-level helpers. Nothing is extracted now; the generic-shaped candidates (`Base64`, `StringUtil`, `TableUtil`, `Sort`) get a fresh per-file screen with tests and provenance when a concrete consumer exists. |
| Gameplay, accounts, payments, navigation, cache tables, operations and SDKs | Excluded | These are application/game systems, private deployment concerns or third-party integrations, not framework migration targets. |

## Legacy lifecycle audit

Item-by-item comparison of the legacy `FogsProcess`/`d_*` mains against Mistlane `Node` (checked against both sources on 2026-10-18):

| Lifecycle item | Legacy behavior | Mistlane behavior | Verdict |
|---|---|---|---|
| Startup entry | `main()` parses program options (Lua config file, log config, process index), configures log4cxx, registers global `mysql_init`/`mysql_end`, then runs `initGlobal`/`initSysCounter`/`checkProtocol` as ordered boolean checks. | CLI parsing and `Node` construction perform all initialization synchronously; any failure throws and the process exits without a partially started state. The Lua config file and process index are replaced by instance env files plus CLI flags. | Reimplemented with a different contract |
| Thread model | `FogsProcess::start` spawns one `boost::thread` per extra `IServer` plus an `io_service::run` thread while all signals are blocked; `main` then blocks in `sigwait`. | One `io_context` drives TCP roles end to end; web transports add a single worker thread. There are no per-server threads. | Simplified |
| Signal set | `sigwait` for `SIGINT`, `SIGQUIT` and `SIGTERM`; other signals keep their defaults except a mask held only while threads spawn. | `asio::signal_set` handles `SIGINT`, `SIGTERM` and `SIGHUP` on the event loop; `SIGQUIT` is deliberately left as a crash path for the Crashpad handler. | Different contract |
| Hot reload | Not present. | `SIGHUP` swaps the Lua VM only after the replacement module loads and initializes; a failure retains the previous VM and module state. | New capability |
| Shutdown entry | `sigwait` returns and `shutdown()` sets a state flag, stops the main server, then polls every 100 ms for `serverConns_` to drain, logging per second and force-removing leftovers after 30 seconds. | The signal handler calls `stop()`: readiness is cleared, the acceptor and probe listener close, the Lua tick stops, Redis and the web stack stop, every session is stopped in order, and the Lua `shutdown` callback runs; each callback is wrapped so one failure logs and shutdown continues. | Reimplemented; no fixed force-kill window |
| IO/thread teardown | After the drain loop an `io_service::stop` is posted, each extra server gets `shutdown(0)`, then `join_all`. | Sessions finish their cancellation handlers before `Node` state is destroyed; the io context drains and the optional worker thread is joined. | Equivalent ordering via a different mechanism |
| Exception paths | Initialization steps return booleans and exit with `EXIT_FAILURE`; shutdown-time exceptions are not wrapped. | Constructor and CLI failures are caught in `main` and exit non-zero; web startup errors are captured, stop the node, then rethrown; stop/shutdown callbacks catch and log instead of unwinding out of the loop. | Stronger than legacy |

## Legacy Lua callback audit

Mapping of the legacy `LuaCallHandler` global-callback surface to Mistlane `LuaService` hooks (checked against both sources on 2026-10-18):

| Legacy global callback | Legacy signature | Mistlane counterpart | Verdict |
|---|---|---|---|
| `L_initServer` | `(processIndex)` called once at startup with the process index | `init(context)` module hook; process identity is a `ServiceContext` table (role, transport, route epoch), no numeric index | Reimplemented with a different contract |
| *(start phase)* | None; servers began accepting straight after listener start | `start()` hook runs after binding but before the first accept | New ordering capability |
| `L_doTick` | `(wallClockMilliseconds)`, interval owned by the caller | `tick()` on a fixed 100 ms steady timer, no argument | Reimplemented; simplified surface |
| `L_closeServer` | Called from the shutdown path | Split into `stop()` on the stop signal and `shutdown()` for final Lua teardown | Split into two phases |
| `L_ClientMsg` / `L_ServerMsg` / `L_PreMsg` / `L_LoggerMsg` / `L_OMMsg` / `L_PayMsg` / `L_StateMsg` / `L_onRPC` | `(id, payload)` per message source with an integer return code | Single `message(payload, route)` returning a string; no per-source dispatch and no RPC channel | Replaced with a smaller contract |
| `L_clientOn` / `L_clientOff` / `L_connected` / `L_disConnected` | Session connect/disconnect events with lightuserdata connection handles | Not migrated; sessions are owned by C++ `Session` objects and Lua has no per-connection callbacks | Not migrated (deliberate) |
| `L_Register` / `L_FirstMsg` / `L_Response` | Inter-server registration, first packet and response handlers on lightuserdata connections | Not migrated; upstreams are direct connections with no registration protocol | Not migrated (see peer-registration row) |
| `L_HttpRequest` | `(uri, params, ip)` returning a string, `"{}"` by default | `http(request)` returning a response table (status/headers/body) with `before_request`/`on_error` hooks | Replaced with structured tables |
| `L_payCallBack` | `(uri, params, ip)` | Excluded; payment belongs to the application domain | Excluded |
| `L_onUdpClientMsg` / `L_onUdpServerMsg` | UDP datagram callbacks | Not migrated (see UDP row) | Not migrated |
| `L_SaveTearDown` / `L_OnlineTime` | Save-on-shutdown and uptime reporting | Not migrated; persistence and operations domains are excluded | Not migrated |
| VM and error model | `LuaContext` with `debug.traceback` handler, last-return-integer code convention, `DeadLoopMonitor` thread, local contexts via `lua_newthread` | Single VM holding a registry-referenced module table, exception messages instead of return codes, an instruction-count hook, no Lua threads | Replaced |
| Loaded libraries | base, package, table, os plus `appendLibPath` | base, string, table, math only | Restricted sandbox |
| Hot reload | Not present | `SIGHUP` rebuilds and swaps the VM only when the new module loads and initializes, otherwise the previous VM is retained | New capability |

## Acceptance meaning

“Reimplemented” means a new implementation exists and has a defined contract; it does not mean wire/API compatibility or production validation. “Replaced” means a maintained dependency owns the protocol/pool implementation, with Mistlane providing only an adapter. “Partially replaced” and “not migrated” are explicit gaps. The historical cross-server overload crash has not been reproduced or diagnosed; local admission controls do not prove a capacity fix.

## Reusable upstream facilities

The current dependency baseline includes Boost 1.92.0, so Asio timers, fixed-size thread pools, UDP sockets, Boost.Log and Boost.Redis are available upstream. Boost.Redis is an Asio-native RESP3 client with reconnect and Sentinel support; Mistlane enables it for optional asynchronous Lua Streams access. Drogon 1.9.14 provides an HTTP worker pool and an optional asynchronous Redis client, which remains disabled to avoid maintaining two clients. Lua-facing lifecycle, request caps and shutdown integration remain adapter responsibilities. Drogon's ORM/MySQL feature stays disabled because the project already uses Boost.MySQL's connection pool.

References: [Boost.Asio thread pool](https://www.boost.org/doc/libs/1_92_0/doc/html/boost_asio/reference/thread_pool.html), [Asio steady timer](https://www.boost.org/doc/libs/1_92_0/doc/html/boost_asio/reference/steady_timer.html), [Asio UDP socket](https://www.boost.org/doc/libs/1_92_0/doc/html/boost_asio/basic_datagram_socket.html), [Boost.Redis](https://www.boost.org/doc/libs/1_92_0/libs/redis/doc/html/redis/index.html), [Boost.Redis Sentinel](https://www.boost.org/doc/libs/1_92_0/libs/redis/doc/html/redis/sentinel.html), [Boost.Log](https://www.boost.org/doc/libs/1_92_0/libs/log/doc/html/log/design.html), and [Drogon Redis support](https://github.com/drogonframework/drogon/wiki/ENG-18-Redis).

## Extraction naming and provenance

Public package paths and filenames use the Mistlane namespace and do not inherit legacy product prefixes. Renaming a path does not change source provenance: reused material and adapted third-party files remain identified in `NOTICE` and `THIRD_PARTY.md`. Do not include legacy source files in the export package merely to document a design reference.

As of 2026-10-18 no generic module carries a migration approval: MinHeap is extracted, and every other legacy utility was excluded by the screening above, so there are no split-out implementation tasks to define. Any future approval must land as its own task stating the public interface, the license provenance and independent acceptance criteria before code is written.
